# 内置 HTTP 服务 / 局域网浏览器访问 —— 影响范围评估

> 评估对象：工程合同台账与拨款管理平台（Rust / egui 桌面版），版本基线 **0.3.2**（R-46 已完成；评估时基线，当前代码已到 0.3.3）
> 评估性质：**只读评估**，未修改任何业务代码
> 评估日期：2026-11-09

---

## 0. 一句话结论

技术上可行，但**这不是"加一个 HTTP 服务"，而是把单机桌面应用改造成 C/S 架构**。

好消息是数据库层已经具备了多客户端安全的基础（WAL + `BEGIN IMMEDIATE` + `version` 乐观锁 + 单号唯一索引），所以"多设备并发写坏账"的风险远低于同类项目。真正的成本集中在三处：

1. **UI 呈现层**——9,531 行 egui 立即模式代码，浏览器里一行都用不上，必须"复用编译"或"重写"二选一；
2. **数据访问边界**——现在所有读写都是 UI 线程上的同步 `&mut Connection` 调用，联网后要变成异步、可跨进程；
3. **联网才暴露的三个硬缺口**——权限校验只在界面层、审计身份写死"界面用户"、打印绑死 Windows GDI。

| 维度 | 判断 | 等级 |
|---|---|---|
| 技术可行性 | 可行，无原理性障碍 | — |
| 数据库并发安全 | 基础已具备，需补 4 项机制 | 🟢 低 |
| 界面一致性 | 取决于路线：复用编译=高一致；重写=长期双维护 | 🔴 高（成本） |
| 权限与审计 | 当前设计**不能**直接对外，必须改 | 🔴 高 |
| 打印 | 浏览器端完全不可用，必须新增 PDF 通道 | 🔴 高 |
| 服务生命周期 | 随界面进程存活，关界面即断服务 | 🟡 中 |
| 工作量（推荐路线） | 约 22–32 人日，含测试与验收 | — |

## 1. 现状基线（评估依据）

| 事实 | 证据 |

**两个关键推论**

- **业务规则天然单源**：合同、拨款、额度、作废、审计等规则只在 `ctp-app` 里实现一次。只要两端都调这些函数，"业务行为一致"就是白送的，不需要靠约定维护。
- **呈现层零复用**：egui 是立即模式自绘 UI，没有 HTML/CSS/JS。所谓"界面一致"，本质上是一个**技术路线选择题**，不是打磨问题。

## 2. 需求本质拆解

需求里同时装了三件不同量级的事，必须拆开看：

| 子需求 | 实际含义 | 主要成本 |
|---|---|---|
| 内置并开启 HTTP 服务 | 进程内起一个监听端口 + 路由 + 鉴权 + 静态资源 | 中 |
| 远程浏览器支持**全部核心业务** | 写操作对外暴露 → 服务端权限校验、身份、审计必须重建 | 高（安全） |
| 界面与交互**尽量一致** | UI 层复用或重写 | **最高** |
| 本机照常使用 | **双端并行**：同一数据库、两套客户端、两套内存状态 | 中 |

因此评估的重点不是"能不能起服务"（能），而是"在双端并行前提下，一致性、权限、打印怎么办"。

## 3. 三条技术路线（互斥选择）

### 路线 A：egui → WebAssembly，复用整套 UI 代码 ⭐ 推荐

把 `ctp-gui` 编译成 `wasm32-unknown-unknown`（eframe 0.29 官方支持 web 目标），浏览器里运行**同一份** UI 代码；数据访问从"直连 SQLite"换成"调用本机 HTTP API"。

- **一致性**：天然达成——同一份布局、同一套弹窗、同一套校验时序、同一套配色。
- **改造点**：`App::exec / read / refresh` 三处抽象成 trait（本地实现直连库，Web 实现走 HTTP）；21 处回调调用点改为"发起请求 + 下一帧取结果"；`rfd` 换成浏览器下载/上传；字体必须**内嵌**（`fonts.rs` 读的是 `C:\Windows\Fonts`，浏览器里没有）；`rusqlite` 不能进 wasm，需要拆出 `ctp-api-types` + `ctp-client` 两个 crate。
- **代价**：wasm 包体（内嵌 CJK 字体后约 8–15 MB，可子集化压缩）；首屏加载几秒；调试链路变长。
- **适合**：本项目这种"界面复杂、用户量小、要求高保真"的场景。

### 路线 B：远程渲染（服务端出画面，浏览器收帧 + 回传输入）

服务端跑 egui，把每帧编码成图片/视频流推给浏览器，浏览器把鼠标键盘回传。

- **一致性**：像素级 100%，一天就能做出能看的原型。
- **硬伤**：中文输入法（IME）在纯 canvas 上体验很差；每客户端吃一份 CPU（1600×1000@15fps，办公机上 1–2 个会话就满）；无法选中复制文字；无原生滚动；断线重连体验差。
- **定位**：只适合"2–3 人远程查看/验收"，**不适合"全部核心业务在浏览器里操作"**。建议只作为 2 人日的技术验证或临时过渡，不做正式方案。

### 路线 C：独立 Web 前端 + JSON API

新增 `ctp-api`（axum）+ 全新前端（Vue/React 或 Leptos/Yew）。

- **优势**：长期最稳，可扩展，并发好，移动端友好，前端可交给专职前端。
- **代价**：等于把 3,383 行页面 + 3,405 行弹窗 + 926 行控件语义**重写一遍**，且此后**双份维护**——每次改版要做两遍，一致性靠流程保证而非代码保证。
- **适合**：用户数会增长到 10+ 并发、或需要手机端、或计划把桌面版逐步淘汰。

### 对比

| 项 | A（wasm 复用） | B（远程渲染） | C（重写前端） |
|---|---|---|---|
| 界面一致性 | 高（同源） | 极高（像素级） | 中（靠对齐） |
| 工作量 | 22–32 人日 | 3–5 人日（但能力不达标） | 45–65 人日 |
| 并发能力 | 好（服务端只出数据） | 差（每人一份 CPU） | 最好 |
| 中文字输入 | 正常 | **差** | 正常 |
| 长期维护 | 单份 | 单份 | **双份** |
| 移动端 | 勉强 | 差 | 好 |

**结论：A 是唯一能在可接受成本内达成"完整业务 + 一致体验"的路线；C 是规模上来后的正确终态；B 只做验证。**

## 4. 五个必答维度

### 4.1 单机与多端并行的兼容性

**结论：兼容，但需要引入"变更感知"，否则桌面端会长期显示旧数据。**

- **进程模型**：桌面进程 = GUI + HTTP 服务同进程。两个客户端（本机 egui、远程浏览器）各自持有数据快照，互不可见。
- **数据层**：两个客户端最终都写同一个 `data/ctp.db`。SQLite WAL 允许"多读 + 单写"，同进程/跨进程都成立，因此**数据不会打架**。
- **真正的坑在内存缓存**：`App` 把 `summaries / payments / categories / periods` 全量载入内存，只在**本端写操作后**调用 `refresh()`（`main.rs:584`）。远程改了一条合同，桌面端如果不刷新，会一直显示旧值——包括"可付额度"这种会直接导致**超额拨款**判断错误的字段。
- **必须补的两件事**：
  1. 轮询 `PRAGMA data_version`（每连接独立计数，其他连接提交后会变），1–2 秒一次，变了就 `refresh()`；
  2. 弹窗打开期间不打断，只置"数据已更新"角标，关闭弹窗后再刷新（避免用户填到一半表单被重置）。
- **UI 线程阻塞**：`app.exec()` 在绘制中同步执行，批量导入几千行会卡住界面。同进程服务端若共享同一条 `Connection`，浏览器请求也会一起卡住。**服务端必须用独立连接池（2–4 条），不能复用 GUI 那条。**

**风险等级：🟡 中**（机制清晰，但必须做，漏做会直接产生错账）。

### 4.2 多设备并发下的数据共享与状态一致性

**结论：本项目的数据层基础是同类项目里少见的扎实，主要缺口在"冲突提示"和"长事务"两点。**

已有的保障（无需重做）：

| 机制 | 效果 |
|---|---|
| WAL 模式 | 读写不互斥，浏览器查询不会挡住桌面端写入 |
| 全部写操作 `BEGIN IMMEDIATE` | 写-写串行化，额度校验与落单在同一事务内，**不会超额** |
| `version` 乐观锁 + `n==0` 报错 | 两人改同一合同时，后提交者收到失败而非静默覆盖 |
| `ux_contract_no` / `ux_payment_no` 唯一索引 | 并发建单不会出现重复单号 |
| `sys_sequence` 原子自增 | 单号分配无竞态 |

需要补的四项：

1. **冲突提示的用户语言**：现在抛的是 `StoreError::Inconsistent("...已被并发修改（期望版本 N）")`，直接弹给用户是技术话术。应转成"该合同已被他人修改，已为您载入最新数据，请重新确认"并自动重载。
2. **写忙超时**：`busy_timeout=5000` 对"两个人手工录单"够用，对"批量导入 3,000 行"不够——后者可能持有写锁数秒，其他写入直接报 `database is locked`。建议提到 15 s，并对写失败做一次自动重试。
3. **写操作排队**（10+ 并发时才需要）：用一个写队列（单写者 actor）替代"人人抢锁"，把 SQLite 的写串行化显式化，避免抖动。
4. **备份口径**：库是单文件，运行中直接复制 `.db` 会拿到不一致副本。多人使用后必须改为 `VACUUM INTO` 或"暂停写入 → 备份"。**当前没有备份功能，这是新增的运维要求。**

**风险等级：🟢 低**（数据安全由现有机制兜住；🟡 仅限"提示体验"和"长事务"两项）。

### 4.3 HTTP 服务的启停与局域网访问约束

**结论：默认必须关闭，开启要做成"显式 + 可解释 + 可回退"的动作；服务生命周期是需求自带的硬约束。**

必须明确的产品决策：

| 项 | 建议口径 | 理由 |
|---|---|---|
| 默认状态 | **关闭** | 打开软件即对外暴露一个含全部合同金额与附件的库，不可接受 |
| 开关位置 | 自检与设置页，独立分区「局域网访问」 | 与"超付容差"同级的系统级设置 |
| 开启动作 | 二次确认弹窗，明示"局域网内其他机器将可以查看/修改本合同台账" | 避免误触 |
| 绑定地址 | 默认**指定内网网卡 IP**，而非 `0.0.0.0` | `0.0.0.0` 会连带暴露给 VPN、热点、虚拟网卡 |
| 端口 | 默认 8080，冲突时提示并允许改 | 需检测占用并给出可读错误 |
| 访问模式 | 「只读」/「只读 + 写入」两档 | 现场常见诉求：领导只看不填 |
| 白名单 | 可选 CIDR 白名单 | 低成本换来的有效收敛 |
| 传输安全 | 明示"仅限可信内网"；如需更高，前置反向代理做 HTTPS | 内置 TLS 会带来证书管理负担 |

生命周期与运维约束（容易被忽略，但会直接变成投诉）：

- **关界面 = 断服务**。需求说"内置"，那服务就活在 GUI 进程里；本机用户点右上角关闭，远程全部掉线。若需要 7×24 供他人访问，必须提供 **`--headless` 仅服务模式**或注册为 Windows 服务/计划任务。**这是需要拍板的第一项。**
- **Windows 防火墙**：首次监听会弹系统授权框；无人值守时需预置 `netsh advfirewall` 规则。
- **休眠/待机**：机器睡眠会断开所有远程连接，需在文档里写明并建议关闭睡眠。
- **IP 漂移**：DHCP 换 IP 后书签失效，建议固定 IP 或用主机名（mDNS）。
- **单实例**：当前无单实例保护，开两个实例会抢同一端口、且两份内存缓存各自为政。建议加文件锁或端口占用检测后提示"程序已在运行"。

**风险等级：🟡 中**（技术不难，产品口径必须先定）。

### 4.4 界面一致性涉及的模块调整范围

**这条路线的选择直接决定调整范围。按推荐路线 A 拆：**

| 模块 | 行数 | 是否需要改 | 改什么 |
|---|---|---|---|
| `main.rs`（App 状态机、导航、顶栏） | 1,561 | **要** | 数据访问抽象、`refresh()` 变更感知、`--headless` 分支、服务启动/停止、窗口/DPR 适配 |
| `dialogs.rs`（11 个弹窗、表单、校验） | 3,405 | **要** | 12 处 `app.exec/read` 改异步；`rfd` 保存/打开 → 浏览器下载/上传；`Instant` 计时在多端可用但需复核 |
| `screens/contracts.rs`（台账、筛选、导出选列） | 931 | 少量 | 1 处写调用异步化；窄屏阈值重标 |
| `screens/payments.rs`（拨款、批量打印、导入） | 853 | 少量 | 同上；批量导入改后台任务 + 进度 |
| `screens/reports.rs`（汇总统计） | 411 | 少量 | 查询改异步（依赖 1 处 `summary_of`） |
| `screens/dashboard.rs` | 414 | 少量 | 同上 |
| `screens/logs.rs` | 311 | 少量 | 3 处查询/清理异步化 |
| `screens/checks.rs` | 204 | 少量 | 改密码、局域网开关 |
| `screens/login.rs` | 228 | **要** | 改为服务端会话登录（见 4.5 W2） |
| `widgets.rs`（自绘表格、按钮、徽标） | 926 | 基本不用 | 自绘控件不依赖系统 UI，浏览器里表现一致（这是 A 路线的额外红利） |
| `theme.rs` / `fonts.rs` | 256 | **字体要** | 必须内嵌 CJK 字体并做子集化；主题色不用改 |
| `paper.rs` / `print`（版面） | — | **要** | 新增 PDF 画布实现（`Canvas` 只有 4 个方法，抽象是现成的） |

**若走路线 C**：上表"少量/基本不用"全部变成"重写"——需要逐屏复刻列宽、行高、合计行样式、空态文案、校验时机、弹窗层级、窄屏折叠规则。**这才是"界面一致"的主要成本所在，且永久双份维护。**

**一致性还有几个具体差异点，必看：**

1. **字体**：桌面读 `msyh.ttc`，浏览器拿不到；不内嵌就是满屏方块。子集化后约 2–4 MB。
2. **文件对话框**：`rfd`（5 处，附件上传、Excel 导出、备份）在浏览器里不存在，必须换成 `<input type=file>` / Blob 下载。**这 5 处是行为差异最容易被用户感知的地方**（下载走浏览器下载目录，不是用户选的路径）。
3. **打印预览**：现在是"服务端渲染位图 → egui 里显示"，浏览器里可以继续显示同一张位图，但**出纸必须换 PDF 通道**。
4. **窗口尺寸**：浏览器窗口宽度不可控，`narrow` 折叠阈值需重标；触摸/小屏建议本期显式排除。
5. **快捷键/剪贴板**：浏览器会拦截部分组合键，需逐一复核。

**风险等级：🔴 高**（成本高，但走 A 可把"重复实现"降为零，只留"适配"）。

### 4.5 边界条件与风险登记

| ID | 风险 | 触发条件 | 后果 | 等级 | 处置 |
|---|---|---|---|---|---|
| **W1** | 权限只在界面层 | 任何人用 HTTP 直接 POST | 绕过 UI 写库，浏览用户变管理员 | 🔴 | 服务端中间件按角色强制校验，**逐接口**覆盖，不能只靠隐藏按钮 |
| **W2** | 无身份、无会话 | 多端登录 | 审计全是"界面用户"，无法追责 | 🔴 | 引入会话（HttpOnly Cookie）+ 操作人标识；审计 `operator` 改为真实来源 |
| **W3** | 共享弱密码 | 初始密码 `0001` 从未改 | 局域网内任何人可登录并改数据 | 🔴 | 开启局域网时强制要求改密码 + 登录失败限流 |
| **W4** | 明文 HTTP | 局域网抓包 | 密码与合同金额可被嗅探 | 🔴 | 文档明示 + 可选反向代理 HTTPS；至少限定绑定网卡 |
| **W5** | 打印不可用 | 远程点"打印" | GDI 只在 Windows 本机可用 | 🔴 | 新增 PDF 画布（3–5 人日），浏览器下载/预览后自行打印 |
| **W6** | UI 线程阻塞拖垮服务 | 批量导入、大附件上传 | 本机卡顿 + 远程超时 | 🟡 | 服务端独立连接池；重活放后台线程；导入显示进度 |
| **W7** | 缓存陈旧导致误判 | 远程改额度，本机未刷新 | **可能超额拨款** | 🟡 | `data_version` 轮询 + 关键页面前置刷新 |
| **W8** | 并发编辑冲突话术生硬 | 两人同时改同一合同 | 用户不理解为何失败 | 🟡 | 冲突 → 自动重载 + 人话提示 |
| **W9** | 附件并发/超大 | 50 MB 上传、同类型重复 | 唯一索引冲突、内存峰值 | 🟡 | 流式上传 + 明确大小上限 + 冲突提示"该类型附件已存在" |
| **W10** | Excel 导出路径 | 浏览器端导出 | 写本地磁盘的路径无意义 | 🟡 | 改为返回字节流下载；审计日志的 `file` 字段记为"浏览器下载" |
| **W11** | 端口/防火墙/IP 变化 | 部署环境 | 连不上，且错误不可读 | 🟢 | 启动自检 + 可读错误 + 文档 |
| **W12** | 运行中拷库备份 | 运维习惯 | 拿到不一致副本 | 🟢 | 提供 `VACUUM INTO` 备份按钮 |
| **W13** | 服务随界面退出 | 本机用户关闭窗口 | 远程全断 | 🟡 | `--headless` 模式或服务化 |

## 5. 改造清单

### P0（不做就不能上线）

1. **新增 `ctp-api` crate**：axum 路由 + 会话中间件 + 服务端权限校验 + 统一错误映射（`StoreError`/`DomainError` → HTTP 状态 + 中文文案，**复用现有文案，不另写一套**）。
2. **身份与会话**：`sys_meta` 已是键值表，可先落"会话密钥 + 操作人"而不改表结构；`operator` 从硬编码改为真实来源（`本机:管理员` / `远程:x.x.x.x:名称`）。
3. **数据访问抽象**：`App` 的 `read/exec/refresh` 抽成 trait，本地实现保持直连，Web 实现走 HTTP。
4. **打印 PDF 通道**：新增 `pdf.rs` 实现 `paper::Canvas`（`line/rect/draw_text/measure_text`），内嵌思源宋体子集，A4 横向，CUPS/浏览器打印。
5. **局域网开关**：默认关闭、二次确认、绑定指定网卡、端口检测、只读/读写两档。

### P1（上线后一周内）

6. `data_version` 轮询与"数据已更新"角标。
7. 冲突重载与人话提示；`busy_timeout` 提到 15 s。
8. 附件流式上传/下载（Go/多 MB 场景）、Excel 改字节流下载。
9. 登录失败限流、开启局域网时强制改初始密码。
10. `--headless` 仅服务模式 + 单实例检测。

### P2（稳定后）

11. 写队列（10+ 并发）、`VACUUM INTO` 备份按钮、CIDR 白名单、审计按来源筛选。

## 6. 可直接执行的验证步骤

按关卡推进，**第 1 关不过就不要往下做**。

**第 1 关：可行性冒烟（0.5 人日）**

```bash
# 1) 确认 egui/eframe 能出 wasm（不改业务代码，先建最小壳）
rustup target add wasm32-unknown-unknown
cargo build -p ctp-gui --target wasm32-unknown-unknown   # 预期报错点即"需要抽象的边界"
# 2) 起一个空 axum 服务，确认端口/防火墙/局域网可达
curl -v http://<本机内网IP>:8080/health
```

判据：能列出所有 `cfg` 冲突点（`rusqlite`、`rfd`、`std::fs`、`raw_window_handle`），且局域网另一台机器能访问 `/health`。

**第 2 关：数据一致性（1 人日）**

```bash
cargo test --workspace --locked          # 基线 152 passed / 1 ignored 必须仍全绿
# 并发写入压测：两个客户端各建 100 张拨款单，校验
#   - 无重复 payment_no
#   - 合同累计已付 == 明细之和
#   - 无 database is locked 未处理异常
```

判据：单号无重复、`reconcile` 无差异、无静默丢写。

**第 3 关：权限与审计（1 人日）**

```bash
# 用浏览用户会话直接 POST 写接口（绕过 UI）
curl -X POST -b "cookie=浏览用户会话" http://127.0.0.1:8080/api/contracts -d @new.json
# 预期 403；且 sys_audit_log 有任何写入都必须带真实 operator
```

判据：所有写接口在服务端拒绝越权；审计 `operator` 不再是"界面用户"。

**第 4 关：端到端验收（2–3 人日）**

- 本机桌面 + 两台远程浏览器同时操作：建合同 → 登记审计价 → 拨款 → 作废 → 导出 Excel → 打印 PDF。
- 交叉验证：A 端写入后，B 端 2 秒内看到；A 端改额度后，B 端拨款时额度校验按新值。
- 打印：PDF 与现有 A4 横向两张表逐像素比对（现有 `CTP_SHOT` 机制可复用截图）。

## 8. 假设与不确定项

| # | 假设 | 若不成立的影响 |
|---|---|---|
| A1 | 局域网并发用户数 **≤ 10**，以"看 + 少量录单"为主 | 若更多或高频写入，需提前做写队列与连接池调优，+3–5 人日 |

## 9. 最终建议

**分三步走，先把不可逆的架构决策做对，再谈界面。**

1. **先做 3 天技术验证（路线 A 的 1 个页面）**：把"合同台账"一页跑通 wasm + HTTP，验证包体、首屏、中文输入、表格滚动。这 3 天决定后面 30 天是否值得投入；若不达标，直接转路线 C，不要硬撑。
2. **验证通过后，按 P0 清单推进**，其中**权限与会话必须与服务端一起落地**，不能"先上线再补"——联网后的越权是真事故，不是体验问题。
3. **打印单独排期**：它是唯一需要写新代码而非改适配的地方，且验收标准是"纸面一致"，必须留出比对时间。

**建议同时明确一条产品红线**：浏览器端本期**只支持"只读"与"读写"两档中的一档**，默认只读。理由是——在身份、审计、TLS 三项补齐之前，把写权限开放给整个局域网，风险与收益不成比例。

## 10. 需要拍板的四项

| # | 决策 | 选项 | 影响 |
|---|---|---|---|
| D1 | 技术路线 | A（wasm 复用，推荐）/ B（远程渲染，仅验证）/ C（重写前端） | 决定工作量是 30 人日还是 60 人日，以及是否长期双维护 |
| D2 | 身份模型 | ① 共用管理员密码 + 记录来源（改动最小）② 引入多用户与角色（需动 schema 与权限口径） | 决定审计能否追责、是否需要数据库迁移 |
| D3 | 服务生命周期 | ① 随界面进程（关窗即断）② 独立 headless 常驻 ③ 注册为 Windows 服务 | 决定远程可用性承诺，以及是否要做单实例/服务化 |
| D4 | 远程写权限 | ① 本期只读 ② 只读 + 读写两档 ③ 直接全开 | 决定 P0 安全项能否延后 |

在这四项未定之前，任何实现都有一半概率返工。**建议先定 D1 与 D4，再启动技术验证。**
